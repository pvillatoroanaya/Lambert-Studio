Lambert Studio

An application for orbit determination and interplanetary mission design, built on Lambert's problem. This report records how it was built, what was found along the way, how well it performs, and how to present it.

Summary

Lambert Studio turns two measurements into an answer. Given two sightings of a satellite from a ground station, it finds the satellite's complete orbit. Given two planets and a launch date, it plans the transfer, including routes that use gravity assists, and it draws everything in 3D with real planetary positions from NASA/JPL.

It grew from a university assignment on Lambert's problem (Curtis, Orbital Mechanics for Engineering Students). The assignment deliverable, a single Python file, is kept and still passes its own self-test. The Studio is the extended version: a desktop application with a web-based interface, a physics engine in Python, live satellite and asteroid data, an interactive Learn section, and a standalone Windows build that runs without Python.

How it works

The physics lives in Python and the picture lives in the browser. A small local server connects them. Nothing leaves the computer except requests for public data.

Interface

HTML, CSS and JavaScript. Three.js draws the 3D scenes on one shared renderer; Plotly draws the charts.

↔

Local server

23 JSON routes on 127.0.0.1. Validates every input and returns plain errors a person can act on.

↔

Physics engine

Python with NumPy and SciPy: Lambert solver, orbit elements, patched-conic flybys, an n-body check.

JPL DE440s ephemerisCelesTrak satellite elementsJPL Small-Body DatabaseJPL CNEOS close approachesJPL Horizons paths

The app opens in an Edge window (app mode, no browser chrome). On the standalone build the same code runs from a packaged folder with its own Python, so the audience needs nothing installed.

The methods

PartMethod
Lambert's problemUniversal-variable formulation (Curtis, Algorithm 5.2) with Stumpff functions and a bracketed root finder; multi-revolution solutions for long transfers
Orbit from sightingsAzimuth, elevation and range become a position in the station frame, then in the Earth-fixed and inertial frames; two positions and the time between them feed the solver
Planet positionsNASA/JPL DE440s through Skyfield, with a built-in approximation if the file is missing
Interplanetary transfersThe same Lambert solver around the Sun; launch energy C3, arrival speed, capture burn; porkchop plots over a grid of dates
Gravity assistsPatched conics, up to four flybys, loops around the Sun allowed, optimisation of dates, plus a deep-space burn variant (Juno-style)
Course checkThe designed route is flown again under full solar-system gravity with trajectory-correction burns
SatellitesKepler motion with the J2 secular drift, compared against SGP4 in the validation suite
UncertaintyMonte Carlo: the orbit is re-solved thousands of times with random measurement errors

Build process

Work on the Studio ran from 29 September to 4 October, from a working assignment to a packaged application. The history below comes from the project's git log and the working notes.

29 Sep
Safe start

Backed up the original folder, restored missing modules, and kept the assignment's single-file build as the hand-in path. Built the new interface (Python server, Three.js and Plotly front end) with the solar system, satellites and asteroids.

30 Sep
Mission design grows

Multi-revolution Lambert solutions, repeat flybys (Galileo, Cassini presets), mission playback, route suggestions with launch windows, a flyby close-up, the Learn section, deep-space burns, launch-vehicle curves and an uncertainty study. First case-study report and LinkedIn carousel.

1 Oct
Fidelity and reports

Higher-fidelity forces and a full solar-system gravity check. Reports in English and Spanish. A full input sweep of every view found and fixed a set of input errors.

3 Oct
Focus and redesign

Removed three views that were more than the project needed. Redesigned the interface (bright theme, start page, icon sidebar, section cards), reorganised the files into src, web, course, tools, added an app icon, built the standalone Windows app, and raised 3D quality with NASA textures.

4 Oct
Performance and this report

Found and fixed the cause of lag on the laptop's integrated graphics, and wrote this report.

Performance

The laptop has an Intel UHD chip and an NVIDIA RTX 4070. Windows gave Edge the Intel chip by default, so the app now asks for the RTX at launch. Frame rate was measured in a hidden Edge window of 1,500 by 900 pixels, five readings per view, with the app's own frame counter. The counter tops out at 144 frames per second.

The Graphics quality setting offers Auto (default), Maximum and Smooth. Auto starts sharp on the RTX, starts lower on integrated graphics, and lowers or raises the resolution within a second or two as the frame rate changes.

What this does not show. The numbers come from a hidden window with no display synchronisation. They show relative cost, not what the real window feels like on battery or with other programs open.

Visual quality

Textures come from NASA's public imagery. Rendering adds supersampling on capable graphics cards, 4x multisampling in the glow pass (2x on integrated graphics), full anisotropic filtering, and higher-detail spheres. The camera button saves the current view as a PNG up to about 3,840 pixels wide.

Presenting it professionally

The thirty-second pitch

"Lambert's problem asks which orbit connects two positions in a given time. I built an application around it. Give it two sightings of a satellite and it finds the orbit. Give it two planets and a date and it plans the trip, with real NASA positions and gravity assists. Every result is checked against textbook and mission figures."

A six-minute demonstration

  1. Start page 0:00Let the Earth turn. Point at the readout: real data sources, live clock. Say what the app does in one sentence, then press Start.
  2. Orbit determination 0:40The assignment data is already solved. Show the two sightings, the 3D orbit, and the elements: a = 28,184.19 km, e = 0.768, i = 20.3°. Say these match the assignment answers.
  3. Uncertainty 1:40Open "How certain is this orbit?" and run the simulations. Explain that small measurement errors grow along the track.
  4. Mission design: porkchop plot 2:30Earth to Mars. Explain the dark eye as the cheapest window and note that every pixel is a separate Lambert solution. Mention that launch windows return every 26 months.
  5. Gravity-assist route and playback 3:30Open the Voyager route and press the play button for the mission playback. Let the flyby close-up play. Say that flybys change speed without fuel.
  6. Full-gravity check 4:40Press "Check in full solar-system gravity". Explain that the simple model is corrected by small burns and that Voyager needs about 4 m/s in total.
  7. Close 5:20Show Satellites or Learn for a few seconds, then return to the start page. Offer the single-file hand-in and the validation suite as proof.

Questions to expect

Why is Lambert's problem useful?It is the core of orbit determination from two positions and of every transfer calculation. The same solver works around the Earth and around the Sun.
How accurate is it?The assignment orbit matches the reference to the digits shown. The Mars case is within 0.01 km/s of a design value, and a full-gravity re-flight lands within 10 km after small corrections.
What is "patched conics"?Each leg is a Sun-centred ellipse and each flyby a planet-centred hyperbola, joined at the planet's sphere of influence. It is the standard first design step. The full-gravity check measures what it leaves out.
Is the data real?Planet positions are NASA/JPL DE440s, satellites are CelesTrak, asteroids are JPL. Offline, the app uses saved copies and says so.
Could it fly a real mission?No. It is a design and teaching tool. Real missions add launch constraints, ephemeris refinement, and operations the app does not model.
What did you build, and what did you use?The solver, validation and application are the project's own. The libraries and data sources are listed in the credits, and AI assistance in building is disclosed there.
What does it need to run?The Windows app needs nothing installed. From source: Python 3.10 or newer and the packages in requirements.txt.
Why did you remove three views?They went beyond the topic. Fewer views made the application easier to explain and to run.

Before you present

  • Plug the laptop in. On battery Windows may switch to the integrated chip.
  • Close other heavy programs and browser windows.
  • Open the app from the desktop shortcut and wait for the start page. The readout should show READY and ONLINE.
  • Press Start once and confirm an orbit appears, then return home with the house icon.
  • In Settings, check Graphics quality is on Auto. Turn on "Show frame rate" if you want to watch it.
  • Keep this report as a PDF and the single-file hand-in on a USB stick as a fallback.
  • If the network is down, say so: the app uses saved data and labels it "saved copy".

Limits and open items

  • Design tool, not flight software. Patched conics and the n-body check are first-design methods.
  • Windows and Edge. The standalone build is Windows only and needs Microsoft Edge installed (it ships with Windows).
  • Graphics memory. The 8K textures use several hundred megabytes of graphics memory; Smooth quality lowers the load on weaker machines.
  • Not yet profiled by hand. Performance was measured in a hidden window. A full session on battery power and on the integrated chip alone has not been timed.
  • Two open items remain in the findings table: the one-off route error and the quick-relaunch behaviour.
  • Reports. The earlier case-study report and LinkedIn carousel in the report folder still describe views that were later removed and show the old interface. Regenerate them before sharing.
